# OpenCLI Violentmonkey Bridge Design

## Goal

Add a local OpenCLI capability that can use Violentmonkey as a controlled script injection channel for Chrome pages.

The primary workflow should be:

```bash
opencli browser work bind
opencli vm inject --session work --file ./script.user.js
opencli vm eval --session work "return document.title"
```

OpenCLI should be able to send a script to the active Chrome page, let a pre-installed Violentmonkey userscript execute it, and receive a structured result or error.

## Chosen Approach

Use a fixed Violentmonkey userscript named `OpenCLI VM Bridge` as the browser-side bridge.

OpenCLI will not drive the Violentmonkey extension UI as the main mechanism. Instead, the user installs the bridge script once. After that, OpenCLI communicates with the bridge through the page using browser commands and a small request/response protocol.

This approach keeps Violentmonkey responsible for userscript privileges and page injection, while OpenCLI stays responsible for command routing, session selection, script parsing, timeouts, and result formatting.

## User-Facing Commands

The first version should expose a small `vm` surface:

```bash
opencli vm bridge-url
opencli vm check --session <name>
opencli vm inject --session <name> --file <path>
opencli vm eval --session <name> <javascript>
opencli vm call --session <name> --function <name> --json <payload>
```

`bridge-url` prints or opens the generated `OpenCLI VM Bridge` install URL. `check` verifies that the bridge is alive on the current page. `inject` loads a `.user.js` or plain JavaScript file and executes it through the bridge. `eval` is a convenience command for small snippets. `call` invokes a named function exposed by a previously injected script.

## Architecture

The integration has three parts:

```text
OpenCLI vm command
  -> OpenCLI browser session
    -> target Chrome tab
      -> OpenCLI VM Bridge userscript
        -> page-context script execution
        -> structured response back to OpenCLI
```

### CLI Layer

The CLI layer resolves the OpenCLI browser session, reads local script files, parses userscript metadata, creates a request envelope, injects the dispatch event into the page, and waits for the bridge response.

Each request includes:

- `requestId`: unique id for correlating responses.
- `nonce`: per-session secret generated by OpenCLI.
- `type`: `ping`, `inject`, `eval`, or `call`.
- `payload`: script source, function name, or JSON arguments.
- `timeoutMs`: execution timeout.

### Bridge Userscript

The bridge userscript runs in Violentmonkey and listens for OpenCLI requests on the page.

It should:

- Validate the request shape.
- Require the current nonce after the handshake.
- Execute supported request types.
- Return `{ requestId, ok, result, error, logs }`.
- Avoid exposing a broad global command surface to arbitrary page scripts.

The bridge should be intentionally small and auditable. It can live as a generated script in the OpenCLI package or as a local user adapter asset.

### Execution Layer

Injected code runs in page context by default, because most automation scripts need direct access to the page DOM and page JavaScript objects.

For userscript-style files, the first version supports a small metadata subset:

- `@name`
- `@match`
- `@include`
- `@exclude`
- `@run-at`
- `@grant`

The MVP can execute only when the current page matches the metadata. Unsupported grants should fail clearly instead of being silently ignored.

## Minimal GM API Support

The first implementation should support only the APIs needed for useful automation:

- `GM_getValue`
- `GM_setValue`
- `GM_deleteValue`
- `GM_listValues`
- `GM_xmlhttpRequest`

Storage can be scoped by script name and origin. `GM_xmlhttpRequest` should be proxied through the bridge, not through arbitrary page `fetch`, so it can keep Violentmonkey's cross-origin behavior where available.

Other APIs, such as menu commands, tabs, notifications, and downloads, are non-goals for the first version.

## Security Model

The bridge must assume that the page itself is untrusted.

Required safeguards:

- Use a request id and nonce for every command.
- Keep the nonce in bridge state, not in a durable page-visible location.
- Accept commands only from the OpenCLI dispatch path.
- Reject commands that exceed size limits.
- Apply a timeout to every execution.
- Return compact errors instead of leaking unrelated page state.

This does not make page injection risk-free. It makes the risk explicit and limits accidental exposure. Users should still treat `vm inject` like running local code against a live browser session.

## Error Handling

Commands should return structured JSON errors for:

- Bridge not installed or not reachable.
- Current page does not match the userscript metadata.
- Unsupported `@grant`.
- Script parse or execution failure.
- Timeout.
- Response nonce or request id mismatch.

Errors should include a concise `hint` when the next action is obvious, such as installing the bridge or binding a browser session.

## Testing

Verification should cover three layers:

- Unit tests for userscript metadata parsing and URL matching.
- Unit tests for request/response envelope validation.
- Browser smoke tests with a local page that installs or simulates the bridge, then runs `check`, `eval`, and `inject`.

Manual verification should also include a real Chrome page with Violentmonkey installed, because extension behavior and page-context injection can differ from a simulated bridge.

## Non-Goals

- Do not automate the Violentmonkey extension UI in the first implementation.
- Do not aim for full Greasemonkey/Tampermonkey compatibility.
- Do not persist arbitrary scripts inside OpenCLI as a script manager.
- Do not bypass OpenCLI's existing browser session model.
- Do not make this a general remote-code execution channel outside explicit user commands.

## Acceptance Criteria

- A user can install the `OpenCLI VM Bridge` userscript once.
- `opencli vm check --session <name>` reports whether the bridge is active on the current tab.
- `opencli vm eval --session <name> "return document.title"` returns the current page title through the bridge.
- `opencli vm inject --session <name> --file ./script.user.js` executes a matching userscript and returns a structured result.
- Unsupported grants and metadata mismatches fail with clear JSON errors.
- The implementation includes parser/envelope tests and at least one browser smoke verification path.
